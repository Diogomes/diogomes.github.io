CI/CD na prática: do commit ao deploy automático

Diogo Gomes  ·  20 de Junho, 2026  ·  3 min de leitura

Antes da automação, soltar uma nova versão de software era um evento tenso: juntava-se semanas de código de várias pessoas, rezava-se para tudo funcionar e o deploy era feito à mão na madrugada. CI/CD inverteu essa lógica. A ideia é integrar e entregar com frequência, em pequenos passos automatizados, para que o software esteja sempre pronto e os erros apareçam cedo, quando ainda são baratos de corrigir.

CI: integração contínua

Continuous Integration significa integrar o código de todo mundo com frequência — várias vezes ao dia — e, a cada integração, rodar automaticamente o build e os testes. Assim, se alguém quebra algo, o time descobre em minutos, não dias depois. Isso depende de um bom uso de branches e Pull Requests.

CD: delivery vs deployment

O "CD" tem dois significados que confundem muita gente, e é comum em entrevista pedir para distinguir os dois:

  • Continuous Delivery — toda mudança aprovada fica pronta para ir a produção a qualquer momento, mas o último passo (apertar o botão) é manual.
  • Continuous Deployment — vai mais longe: cada mudança que passa nos testes vai a produção automaticamente, sem intervenção humana.

Before automation, shipping a new version of software was a tense event: weeks of code from several people were piled together, everyone prayed it would all work, and the deploy was done by hand in the middle of the night. CI/CD flipped that logic. The idea is to integrate and deliver often, in small automated steps, so the software is always ready and errors show up early, while they are still cheap to fix.

CI: continuous integration

Continuous Integration means integrating everyone's code frequently — several times a day — and automatically running the build and tests on every integration. That way, if someone breaks something, the team finds out in minutes, not days later. This depends on good use of branches and Pull Requests.

CD: delivery vs deployment

The "CD" has two meanings that confuse a lot of people, and interviewers often ask you to tell them apart:

  • Continuous Delivery — every approved change is kept ready to go to production at any time, but the last step (pressing the button) is manual.
  • Continuous Deployment — goes further: every change that passes the tests goes to production automatically, with no human intervention.

The stages of a pipeline

A pipeline is a sequence of steps the code goes through, from commit to production. Each step only runs if the previous one passed. A typical flow:

commit → build → testes → empacota (artefato) → deploy staging → deploy produção

Se os testes falham, o pipeline para ali e ninguém precisa investigar um deploy quebrado depois.

Artefatos

O artefato é o resultado empacotado do build — um arquivo .jar, um binário ou, cada vez mais comum, uma imagem de container. A regra de ouro é: construa o artefato uma vez e promova o mesmo artefato por todos os ambientes. Assim você garante que o que foi testado em staging é exatamente o que vai a produção.

O valor real do CI/CD não é "fazer deploy rápido": é encurtar o ciclo de feedback. Quanto antes você descobre que algo quebrou, menor o estrago e mais barato o conserto.

Artifacts

The artifact is the packaged result of the build — a .jar file, a binary or, increasingly common, a container image. The golden rule: build the artifact once and promote the same artifact through every environment. That guarantees that what was tested in staging is exactly what goes to production.

The real value of CI/CD isn't "deploying fast": it's shortening the feedback loop. The sooner you find out something broke, the smaller the damage and the cheaper the fix.

Pipeline example in YAML

Most tools (GitHub Actions, GitLab CI, etc.) describe the pipeline in a YAML file versioned alongside the code:

jobs:
  build-e-teste:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci
      - run: npm test
      - run: npm run build

Por que isso importa

Os ganhos práticos são diretos: feedback rápido (erros aparecem em minutos), menos regressão (testes automáticos pegam o que o humano esqueceria) e deploys previsíveis (o processo é o mesmo toda vez, sem passos manuais que alguém pode errar). Times com bom CI/CD entregam mais e com menos medo.

Conclusão

CI/CD é a espinha dorsal do DevOps moderno: transforma entregas de eventos arriscados em rotina tranquila. Comece entendendo a diferença entre integração e entrega, o que é um artefato e por que o feedback rápido muda tudo. Com isso, você já consegue ler e contribuir com a maioria dos pipelines que vai encontrar.

Why it matters

The practical gains are direct: fast feedback (errors show up in minutes), fewer regressions (automated tests catch what a human would forget) and predictable deploys (the process is the same every time, with no manual steps someone can get wrong). Teams with good CI/CD ship more and with less fear.

Conclusion

CI/CD is the backbone of modern DevOps: it turns releases from risky events into a calm routine. Start by understanding the difference between integration and delivery, what an artifact is and why fast feedback changes everything. With that, you can already read and contribute to most pipelines you will come across.

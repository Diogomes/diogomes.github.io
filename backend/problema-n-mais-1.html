O problema N+1: como o ORM te trai

Diogo Gomes  ·  15 de Junho, 2026  ·  3 min de leitura

O problema N+1 é uma das armadilhas de performance mais comuns no back-end, e o mais traiçoeiro é que o código parece perfeito. Ele nasce da comodidade dos ORMs e só aparece quando o volume de dados cresce. Saber identificá-lo e resolvê-lo é conhecimento esperado de qualquer dev pleno.

O que é o problema N+1

O nome descreve exatamente o que acontece: você faz 1 query para buscar uma lista de itens, e depois N queries — uma para cada item — para buscar dados relacionados. Se você lista 100 pedidos e, para cada um, busca o cliente, são 1 + 100 = 101 queries onde duas bastariam.

Como o ORM te trai

ORMs (Object-Relational Mappers) deixam acessar relações como se fossem atributos comuns. O problema é que cada acesso pode disparar uma query escondida — o chamado lazy loading:

pedidos = Pedido.all()          // 1 query: SELECT * FROM pedidos

for pedido in pedidos:
    print(pedido.cliente.nome)  // N queries! cada .cliente
                                // dispara SELECT * FROM clientes WHERE id = ?

O código é limpo e legível — essa é a traição. Nada indica visualmente que pedido.cliente está indo ao banco a cada iteração. Com 10 pedidos você nem percebe; com 10 mil, a página trava.

Como detectar

A forma mais direta é ligar o log de queries do ORM em ambiente de desenvolvimento. Se você vê dezenas de SELECTs quase idênticos variando só o ID, encontrou um N+1:

SELECT * FROM pedidos;
SELECT * FROM clientes WHERE id = 1;
SELECT * FROM clientes WHERE id = 2;
SELECT * FROM clientes WHERE id = 3;
... (repete N vezes)

No dia a dia isso aparece quando um endpoint que era rápido começa a degradar conforme a base cresce. Ferramentas de APM e o próprio log de queries são seus aliados.

Como resolver: eager loading

A solução é dizer ao ORM, de antemão, que você vai precisar da relação. Isso é o eager loading, que o ORM traduz em um JOIN ou em uma segunda query em lote (batch):

// Antes (N+1):
pedidos = Pedido.all()

// Depois (eager loading):
pedidos = Pedido.all().include('cliente')

// O ORM gera algo como:
// SELECT * FROM pedidos;
// SELECT * FROM clientes WHERE id IN (1, 2, 3, ...);  // 1 query so

Antes e depois: o impacto

CenárioQueries (100 itens)Resultado
Lazy loading (N+1)101Lento, escala mal
Eager loading (JOIN ou IN)1 ou 2Rápido e constante

A diferença não é só velocidade: o N+1 piora linearmente com o número de itens, enquanto o eager loading mantém o custo praticamente constante. É a diferença entre um endpoint que aguenta crescimento e outro que vira gargalo.

O N+1 não é um bug do ORM — é o ORM fazendo exatamente o que você pediu sem perceber. A solução é tornar a intenção explícita: avise que vai precisar da relação.

Quando aceitar e cuidados

Nem todo loop com acesso a relação é um problema: se a lista tem 2 itens, o N+1 é irrelevante. Por outro lado, eager loading exagerado (carregar relações que você não usa) também desperdiça recursos. O equilíbrio é carregar o que você de fato vai usar, em lote. Esse tema conversa diretamente com cache no back-end, outra alavanca de performance.

Conclusão

O problema N+1 é o exemplo perfeito de como abstrações cômodas escondem custos. Aprenda a ler o log de queries, reconheça o padrão de SELECTs repetidos e use eager loading para colapsar N queries em uma. É um daqueles conhecimentos que, uma vez aprendidos, você passa a enxergar em todo lugar.

The N+1 problem is one of the most common performance traps in the back-end, and the sneakiest part is that the code looks perfect. It comes from the convenience of ORMs and only shows up when data volume grows. Knowing how to spot and fix it is expected of any mid-level dev.

What the N+1 problem is

The name describes exactly what happens: you run 1 query to fetch a list of items, and then N queries — one per item — to fetch related data. If you list 100 orders and fetch the customer for each one, that's 1 + 100 = 101 queries where two would do.

How the ORM betrays you

ORMs (Object-Relational Mappers) let you access relations as if they were ordinary attributes. The catch is that each access can trigger a hidden query — so-called lazy loading:

orders = Order.all()            // 1 query: SELECT * FROM orders

for order in orders:
    print(order.customer.name)  // N queries! each .customer
                                // fires SELECT * FROM customers WHERE id = ?

The code is clean and readable — that's the betrayal. Nothing visually indicates that order.customer is hitting the database on every iteration. With 10 orders you won't even notice; with 10 thousand, the page grinds to a halt.

How to detect it

The most direct way is to turn on the ORM's query log in your development environment. If you see dozens of nearly identical SELECTs varying only by ID, you've found an N+1:

SELECT * FROM orders;
SELECT * FROM customers WHERE id = 1;
SELECT * FROM customers WHERE id = 2;
SELECT * FROM customers WHERE id = 3;
... (repeats N times)

Day to day, this shows up when an endpoint that used to be fast starts degrading as the database grows. APM tools and the query log itself are your allies.

How to fix it: eager loading

The fix is to tell the ORM up front that you'll need the relation. This is eager loading, which the ORM translates into a JOIN or a second batched query:

// Before (N+1):
orders = Order.all()

// After (eager loading):
orders = Order.all().include('customer')

// The ORM generates something like:
// SELECT * FROM orders;
// SELECT * FROM customers WHERE id IN (1, 2, 3, ...);  // just 1 query

Before and after: the impact

ScenarioQueries (100 items)Result
Lazy loading (N+1)101Slow, scales poorly
Eager loading (JOIN or IN)1 or 2Fast and constant

The difference isn't just speed: N+1 gets worse linearly with the number of items, while eager loading keeps the cost practically constant. It's the difference between an endpoint that can handle growth and one that becomes a bottleneck.

N+1 isn't an ORM bug — it's the ORM doing exactly what you asked without you noticing. The fix is to make your intent explicit: say up front that you'll need the relation.

When to accept it, and caveats

Not every loop that accesses a relation is a problem: if the list has 2 items, N+1 is irrelevant. On the other hand, excessive eager loading (loading relations you don't use) also wastes resources. The balance is to load what you'll actually use, in batches. This topic ties in directly with caching in the back-end, another performance lever.

Conclusion

The N+1 problem is the perfect example of how convenient abstractions hide costs. Learn to read the query log, recognize the pattern of repeated SELECTs and use eager loading to collapse N queries into one. It's one of those pieces of knowledge that, once learned, you start seeing everywhere.

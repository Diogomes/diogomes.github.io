Autenticação vs Autorização: sessions, JWT e OAuth

Diogo Gomes  ·  17 de Junho, 2026  ·  3 min de leitura

Autenticação e autorização são confundidas o tempo todo, mas resolvem problemas diferentes. Como dev pleno, você precisa não só saber a diferença, mas escolher entre sessões e tokens, entender a estrutura de um JWT e explicar onde OAuth2 entra. Esses temas aparecem em quase toda entrevista de back-end.

Authn vs Authz

Autenticação (authn) responde "quem é você?". Autorização (authz) responde "o que você pode fazer?". A analogia: autenticação é mostrar seu RG na portaria de um prédio; autorização é o crachá que diz a quais andares você pode subir. Você precisa provar quem é antes de descobrir o que pode acessar — primeiro authn, depois authz.

Sessão com cookie

No modelo de sessão, o usuário faz login, o servidor cria uma sessão e guarda o estado dela (em memória, banco ou Redis). Ele devolve um cookie com um ID de sessão. A cada requisição, o navegador envia o cookie, e o servidor procura a sessão correspondente:

login OK -> servidor guarda sessao abc123 { userId: 7 }
        -> Set-Cookie: session=abc123

requisicao -> Cookie: session=abc123
           -> servidor busca abc123, sabe que e o user 7

O ponto-chave: o estado vive no servidor. Isso facilita revogar acessos, mas exige que todos os servidores compartilhem onde a sessão está guardada.

Token JWT

Com JWT (JSON Web Token), o servidor não guarda estado. No login ele gera um token assinado que contém os dados do usuário, e o cliente o envia em cada requisição (geralmente no header Authorization: Bearer ...). O servidor só verifica a assinatura — não precisa consultar nada. Por isso JWT é stateless, o que combina com APIs REST e escala bem horizontalmente.

A estrutura de um JWT

Um JWT tem três partes separadas por ponto: header.payload.signature.

header    -> { "alg": "HS256", "typ": "JWT" }
payload   -> { "sub": 7, "role": "admin", "exp": 1735689600 }
signature -> HMAC(base64(header) + "." + base64(payload), SEGREDO)

Header e payload são apenas base64, não criptografia — qualquer um consegue ler. A assinatura garante que o conteúdo não foi adulterado, porque só quem tem o segredo consegue gerá-la. Daí a regra de ouro: nunca coloque segredos no payload (senhas, dados sensíveis), pois ele é legível.

OAuth2: autorização delegada

OAuth2 resolve outro problema: deixar um app acessar seus dados em outro serviço sem entregar sua senha. É o que acontece no "login com Google". Você é redirecionado ao Google, autentica lá, e o Google devolve ao app um token que autoriza apenas o que você consentiu. O app nunca vê sua senha. Importante: OAuth2 é sobre autorização delegada, não sobre login — embora seja a base de fluxos de login social.

Autenticação prova quem você é; autorização decide o que você faz. Sessão guarda o estado no servidor; JWT carrega o estado no token. Confundir esses pares é o erro mais comum da área.

Notas de segurança

Pontos que sempre valem citar: defina expiração curta nos tokens (claim exp) e use refresh tokens para renovar; use HTTPS sempre; marque cookies como HttpOnly e Secure; e lembre que JWT revogado antes da hora é um problema real — por isso tokens de vida longa são arriscados.

Conclusão

Authn e authz são camadas distintas e complementares. Sessões oferecem controle fácil de revogação; JWTs oferecem statelessness e escala. OAuth2 cuida do acesso delegado. Saber quando usar cada um, e os cuidados de segurança de cada escolha, é exatamente o que se espera de um pleno.

Authentication and authorization get mixed up all the time, but they solve different problems. As a mid-level dev, you need not only to know the difference, but to choose between sessions and tokens, understand the structure of a JWT and explain where OAuth2 fits in. These topics come up in almost every back-end interview.

Authn vs Authz

Authentication (authn) answers "who are you?". Authorization (authz) answers "what are you allowed to do?". The analogy: authentication is showing your ID at a building's front desk; authorization is the badge that says which floors you can go up to. You have to prove who you are before finding out what you can access — authn first, then authz.

Session with a cookie

In the session model, the user logs in, the server creates a session and stores its state (in memory, a database or Redis). It returns a cookie with a session ID. On every request, the browser sends the cookie, and the server looks up the matching session:

login OK -> server stores session abc123 { userId: 7 }
        -> Set-Cookie: session=abc123

request -> Cookie: session=abc123
        -> server looks up abc123, knows it's user 7

The key point: the state lives on the server. This makes revoking access easy, but requires every server to share wherever the session is stored.

JWT tokens

With JWT (JSON Web Token), the server keeps no state. At login it generates a signed token containing the user's data, and the client sends it with every request (usually in the Authorization: Bearer ... header). The server only verifies the signature — it doesn't need to look anything up. That's why JWT is stateless, which fits REST APIs and scales well horizontally.

The structure of a JWT

A JWT has three parts separated by dots: header.payload.signature.

header    -> { "alg": "HS256", "typ": "JWT" }
payload   -> { "sub": 7, "role": "admin", "exp": 1735689600 }
signature -> HMAC(base64(header) + "." + base64(payload), SECRET)

Header and payload are just base64, not encryption — anyone can read them. The signature guarantees the content hasn't been tampered with, because only whoever has the secret can generate it. Hence the golden rule: never put secrets in the payload (passwords, sensitive data), since it's readable.

AspectSession (cookie)JWT (token)
StateOn the server (stateful)In the token (stateless)
Horizontal scalingNeeds a shared storeNatural, no store
RevocationEasy (delete the session)Hard (token is valid until it expires)
Size sentSmall (just the ID)Larger (carries the data)

OAuth2: delegated authorization

OAuth2 solves a different problem: letting an app access your data on another service without handing over your password. It's what happens with "sign in with Google". You're redirected to Google, authenticate there, and Google gives the app a token that authorizes only what you consented to. The app never sees your password. Important: OAuth2 is about delegated authorization, not about login — even though it's the foundation of social login flows.

Authentication proves who you are; authorization decides what you can do. A session keeps state on the server; a JWT carries state in the token. Confusing these pairs is the most common mistake in the field.

Security notes

Points that are always worth mentioning: set a short expiration on tokens (the exp claim) and use refresh tokens to renew them; always use HTTPS; mark cookies as HttpOnly and Secure; and remember that revoking a JWT before its time is a real problem — which is why long-lived tokens are risky.

Conclusion

Authn and authz are distinct, complementary layers. Sessions offer easy revocation; JWTs offer statelessness and scale. OAuth2 handles delegated access. Knowing when to use each one, and the security caveats of each choice, is exactly what's expected of a mid-level engineer.

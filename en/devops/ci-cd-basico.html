CI/CD in practice: from commit to automatic deploy

Diogo Gomes  ·  Jun 20, 2026  ·  3 min read

Before automation, shipping a new version of software was a tense event: weeks of code from several people were piled together, everyone prayed it would all work, and the deploy was done by hand in the middle of the night. CI/CD flipped that logic. The idea is to integrate and deliver often, in small automated steps, so the software is always ready and errors show up early, while they are still cheap to fix.

CI: continuous integration

Continuous Integration means integrating everyone's code frequently — several times a day — and automatically running the build and tests on every integration. That way, if someone breaks something, the team finds out in minutes, not days later. This depends on good use of branches and Pull Requests.

CD: delivery vs deployment

The "CD" has two meanings that confuse a lot of people, and interviewers often ask you to tell them apart:

  • Continuous Delivery — every approved change is kept ready to go to production at any time, but the last step (pressing the button) is manual.
  • Continuous Deployment — goes further: every change that passes the tests goes to production automatically, with no human intervention.
ConceptWhat it automatesProduction deploy
CIBuild + tests on every commitNo
Continuous DeliveryEverything up to being ready to deployManual (one click)
Continuous DeploymentEverything, including the deployAutomatic

The stages of a pipeline

A pipeline is a sequence of steps the code goes through, from commit to production. Each step only runs if the previous one passed. A typical flow:

commit → build → testes → empacota (artefato) → deploy staging → deploy produção

If the tests fail, the pipeline stops right there and nobody has to investigate a broken deploy later.

Artifacts

The artifact is the packaged result of the build — a .jar file, a binary or, increasingly common, a container image. The golden rule: build the artifact once and promote the same artifact through every environment. That guarantees that what was tested in staging is exactly what goes to production.

The real value of CI/CD isn't "deploying fast": it's shortening the feedback loop. The sooner you find out something broke, the smaller the damage and the cheaper the fix.

Pipeline example in YAML

Most tools (GitHub Actions, GitLab CI, etc.) describe the pipeline in a YAML file versioned alongside the code:

jobs:
  build-e-teste:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci
      - run: npm test
      - run: npm run build

Why it matters

The practical gains are direct: fast feedback (errors show up in minutes), fewer regressions (automated tests catch what a human would forget) and predictable deploys (the process is the same every time, with no manual steps someone can get wrong). Teams with good CI/CD ship more and with less fear.

Conclusion

CI/CD is the backbone of modern DevOps: it turns releases from risky events into a calm routine. Start by understanding the difference between integration and delivery, what an artifact is and why fast feedback changes everything. With that, you can already read and contribute to most pipelines you will come across.

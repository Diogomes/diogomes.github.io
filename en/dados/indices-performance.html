Indexes and performance: why your query is slow

Diogo Gomes  ·  Jun 17, 2026  ·  3 min read

Your query worked perfectly with a thousand records, and now, with ten million, it takes thirty seconds. Almost always the explanation lies in indexes — or the lack of them. Understanding indexes is what turns a mid-level professional into someone who writes queries that scale.

The book index analogy

Imagine looking for the word "transaction" in an 800-page book with no index: you read page by page, from start to finish. With the index at the back of the book, you go straight there: "transaction ... p. 412". A database index does exactly that — it's a separate structure that maps values to the location of rows, avoiding a scan of the whole table.

B-tree: the structure behind it

Most indexes use a B-tree (balanced tree). You don't need to implement one, but the idea matters: values are kept sorted in a tree, and the database finds any of them by descending just a few levels — instead of N rows, it makes about log(N) comparisons. That's why an index turns a search over millions of rows into just a handful of steps.

What an index speeds up

Indexes help whenever the database needs to locate or sort data:

  • WHERE — filtering by an indexed column.
  • JOIN — matching rows between tables by the join column.
  • ORDER BY — the data in the index is already sorted.

That's why foreign keys and heavily filtered columns are natural candidates for an index.

The cost: slower writes

An index isn't free magic. Each index is a structure that has to be updated on every INSERT, UPDATE or DELETE. More indexes mean slower writes and more disk space.

OperationWithout indexWith index
Read (WHERE/JOIN)Slow (scans everything)Fast
Write (INSERT/UPDATE)FastSlower (updates the index)
Disk spaceSmallerLarger

The decision to index is always a balance between reads and writes.

Composite index and column order

A composite index covers several columns together, and order matters. Think of a phone book sorted by (last name, first name): it works for searching by last name, or by last name + first name, but it's useless for searching by first name alone. The rule is the "leftmost prefix": the index (a, b) helps with filters on a or on a and b, but not on b alone.

Reading the execution plan (EXPLAIN)

To find out what the database is really doing, use EXPLAIN. It reveals whether the query uses the index (index scan) or scans the whole table (full table scan / seq scan) — the villain of slow queries.

EXPLAIN SELECT * FROM pedidos WHERE cliente_id = 42;

-- Without an index:
-- Seq Scan on pedidos  (cost=0.00..18234 rows=1)

-- After CREATE INDEX idx_cli ON pedidos(cliente_id):
-- Index Scan using idx_cli  (cost=0.42..8.44 rows=1)

The drop in estimated cost shows the gain. When you see "Seq Scan" on a large table filtered by a column, it's the classic sign of a missing index.

An index isn't "the more, the better". It's "which column do I filter on so often that it's worth paying the write cost?". Whoever answers that by reading EXPLAIN, rather than guessing, truly optimizes.

In interviews they often hand you a slow query and ask you to diagnose it — the expected answer starts with "I'd run EXPLAIN to see if there's a full scan". Day to day, this shows up every time a report that used to be instant starts to hang as the table grows.

Conclusion

Indexes speed up reads at the cost of slower writes; B-trees explain why they're so efficient; column order defines what a composite index covers; and EXPLAIN is your X-ray for telling a full scan from an index scan. With that, "my query is slow" stops being a mystery and becomes an objective diagnosis.
